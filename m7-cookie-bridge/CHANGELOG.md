# Changelog

История двух независимых артефактов:

- **плагин Movian** — `RuTracker.org` (`plugin.json` в корне репозитория);
- **расширение браузера** — `Movian Cookie Bridge` (`m7-cookie-bridge/extension/`).

Версии по semver. Изменения сгруппированы «Добавлено / Исправлено / Известные ограничения».

Релизы помечены тегами: `v0.8.0-m7-bridge` (плагин), `ext-v0.3.2` (расширение).
Для 0.9.0 / 0.4.0 теги ещё не ставились.

---

## Плагин — `RuTracker.org`

### 0.9.0 — 2026-10-18

Аудит безопасности, модульная структура, универсальный Cookie Bridge.

**Новый id: `rutracker`** (было `RuTracker.org`). Название `RuTracker.org` и
STPP-пути Bridge не менялись. Последствия:

- Для Movian это **другой плагин**, чем `RuTracker.org` 0.8.0: тот остаётся
  установленным (удалить вручную), его настройки и сессия Bridge не
  переносятся (хранилище плагина — по id), сессию нужно отправить заново.
  Маршруты теперь `rutracker:…` — закладки на `RuTracker.org:…` не откроются.
- Тот же id у старого публичного плагина `Buksa/movian-rutracker` 0.7.5, так
  что для его пользователей это обновление того плагина (0.9.0 > 0.7.5) с
  общим файлом настроек. Его `domain` хранился без схемы (`rutracker.org`) —
  он приводится к `https://rutracker.org`.
- Файлы внутри ZIP: `main.js` и `logo.png` (их задаёт `plugin.json`).

**Безопасность**

- Убран `debug: true` со всех запросов. С ним ядро писало в `movian.log`
  заголовки (`> Cookie: …`) и hexdump POST-тела — то есть **пароль легаси-входа**
  и cookies Bridge. Лог пишется независимо от `-d` и отдаётся без
  аутентификации по `http://<movian>:42000/api/logfile/0` (ещё и с
  `?mode=pastebin` — на публичный pastebin). Проверено живьём: в 0.8.0 все
  cookies сессии были в логе и в `/api/logfile/0`, в 0.9.0 — нет.
- Cookies Bridge уходят только по **https** и только на `rutracker.org` /
  `rutracker.net` (и поддомены). Раньше allow-list расширялся хостом из
  пользовательской настройки домена (любой URL получал сессию), включал
  `rutracker.lib` и сторонний прокси `rutracker-org.appspot.com` и разрешал http.
- Cookie **уходит из дерева настроек** сразу после приёма: в
  `browserCookie` остаётся заглушка `сохранено вне настроек (cookies: N)`, сама
  сессия — в файле `store/rutracker_bridge` плагина. Дерево
  `settings.apps.nodes.*` читается по STPP без аутентификации (LAN и любые
  веб-страницы через `ws://127.0.0.1:42000`) и показывается на экране настроек.
  Сессию, оставленную в дереве настроек старой версией Bridge, модуль
  переносит при старте (для плагинов, переходящих на `movian-session.js`).

**Исправлено**

- Проверка сессии шла по `index.php`, который Cloudflare не защищает: статус
  `authenticated` при том, что разделы и поиск отвечали `403 challenge`.
  Теперь проверяется `viewforum.php?f=7`. Живьём: без `cf_clearance` →
  `challenge`, подменённая `bb_session` → `rejected`.
- Скрипт Cloudflare `/cdn-cgi/challenge-platform/`, который вставляется в
  обычные страницы, больше не считается челленджем.
- Одна проверка на одну передачу (раньше две: cookie и UA приходят двумя SET).
- Изменения основных настроек во время работы сохранялись в файл группы
  `rutracker_bridge` и терялись после перезапуска (`settings.globalSettings()`
  в M7 перенастраивает сам модуль). Обе группы создаются через `new`.
- Страница раздачи падала на длинных постах: `attempt to push beyond currently
  allocated stack` — дефект нативного `textContent` в ядре (`es_gumbo.c`).
  Текст постов читается из строки страницы.
- `:start` показывал аккаунт через раз (глобальная `/g`-регулярка с `lastIndex`).
- Легаси-вход/выход/скачивание меняли общий объект заголовков: все следующие
  GET уходили с `Content-Type: application/x-www-form-urlencoded`,
  `Origin` и `Referer: login.php`.
- Каждая страница раздачи добавляла до трёх никогда не удаляемых
  HTTP-инспекторов (с неэкранированным `?`, которые ничего не матчили).
- Неудачное скачивание `.torrent` (сеть или HTML-страница вместо файла)
  передавалось в torrent-браузер как торрент; теперь — ошибка на странице.
- После ответа на капчу шёл второй редирект на `:start`, затиравший
  страницу капчи; на странице ввода капчи был `http://http://…` и мёртвый
  маршрут `rutracker:start`.
- Размер в списках показывался HTML-ссылкой (`<a …>18.45&nbsp;GB &#8595;</a>`).
- Протухшая сессия Bridge перекрывала успешный вход по логину (cookie
  инспектора побеждает cookie jar ядра); успешный вход теперь очищает Bridge.
- По ревью: вход по логину считается успешным только по редиректу сайта;
  сетевая ошибка и Cloudflare показываются ошибкой, неизвестная страница —
  повторным запросом логина. Выход возвращает на `:start` и сначала очищает
  Bridge, поэтому запрос выхода уходит без сессии браузера — браузер остаётся
  залогинен. Согласие с условиями сохраняется в настройке. Запрос поиска с
  двоеточием больше не режется маршрутом. Инспекторы покрывают оба
  официальных домена при любом выбранном зеркале.
- Пустой результат поиска показывал пустую страницу, и это выглядело как
  поломка. Сайт ищет целые слова («dis» не находит ничего, «dis*» находит
  Discovery), поэтому теперь страница пишет «Ничего не найдено» и предлагает
  повторить запрос со `*`. Если сайт не вернул страницу результатов (сеть,
  Cloudflare), показывается ошибка, а не «Ничего не найдено».
- Если сайт не вернул следующую страницу результатов поиска (сеть, Cloudflare),
  после последней показанной темы пишется «Следующая страница не загружена», и
  пейджинг останавливается. Раньше список молча заканчивался.
- Поисковые ссылки на странице раздачи строятся из названия без `[теги]` и
  обрезаются на `(`, `/`, `|`, `\`: `[Матрица] Осознанность (1999) [1080p]` даёт
  «Осознанность», а не пустой запрос. Если названия не осталось, пункты поиска
  не добавляются.
- Картинка капчи при входе грузилась по `http://`; теперь по `https://`, если
  схема не указана.
- Закладки: если сайт не вернул страницу закладок (сеть, Cloudflare, гостевая
  страница), показывается ошибка; пустой список пишет «Закладок нет».
- Подразделы форума повторялись на каждой странице форума; теперь они только на первой.

**Архитектура**

- Точка входа `main.js` (бывший `RuTracker.org.js`) — только связывание
  слоёв (из 3234 строк, ~1200 из которых были закомментированным старым
  кодом). Иконка плагина — `logo.png` (бывший `RuTracker.org.png`).
- `src/api/` (HTTP, HTML), `src/business/` (каталог, легаси-вход),
  `src/ui/` (настройки, страницы), `src/bridge/rutracker-adapter.js`.
- `vendor/movian-cookie-bridge/` — универсальная часть Bridge для Movian
  (`movian-session.js`) и копия ядра расширения (`bridge-core.js`).
- Удалены мёртвые части: `service.create('config', true)` (регистрировал
  лишний сервис «config»), настройка «Cookie пользователя» и
  `saveUserCookie()` (значение никуда не шло), неиспользуемые функции и stores.
- Удалена настройка «Изображения (webp)»: включённая (по умолчанию), она
  заменяла **каждый** постер раздачи общей иконкой. Movian декодирует WEBP сам
  (определяет по сигнатуре, `fa_imageloader.c`); постеры по прямым ссылкам на
  картинки, включая `.webp`, теперь показываются.
- Удалена настройка «Видимость Torrent-ссылок»: она скрывала только главный
  пункт торрента раздачи (прямая ссылка `dl.php` и magnet оставались), а
  строгая проверка `=== 1` могла скрыть его и при включённой настройке.
  Пункт показывается всегда; сохранённое старое значение игнорируется.

**Известные ограничения** — см. README-M7-COOKIE-BRIDGE.md, «Остаточные
риски»: дыры ядра (STPP без аутентификации, лог по HTTP, TLS без проверки
сертификата) плагином не закрываются. Значения cookies в логе dev-режима
ядра (`-p`, debug) — так задумано: dev-режим показывает всё.

### 0.8.0 — 2026-10-17

Первая версия с Cookie Bridge. База — апстримная 0.7.7 (Wain, fix by kovalDN);
`id`, `file` и `title` не менялись, поэтому обновление поверх установленной копии
проходит как обычный апгрейд.

**Добавлено**

- Группа настроек `rutracker_bridge`: две строки (`browserCookie`, `browserUA`)
  и действие `bridgeClear` («Очистить сессию Cookie Bridge»). ID группы — без точки:
  STPP-пути режутся по `.` (`prop_setdn()` в ядре Movian), поэтому группу самого
  плагина `RuTracker.org` через `/api/stpp` адресовать нельзя.
- Приём cookies и User-Agent по STPP **без перезапуска Movian**: watcher на изменение
  настроек сразу применяет сессию и перепроверяет её.
- `bridgeHostAllowed()` — cookies уходят только на allow-list хостов
  (`rutracker.org`, `rutracker.net`, `rutracker.lib`, `rutracker-org.appspot.com`
  и текущий базовый хост). Редиректы, сторонние картинки и зеркала их не получают.
- `bridgeUA()` — при активном bridge запросы идут с тем же UA, что у браузера-источника
  сессии. Иначе `cf_clearance` не совпадает с UA, который его получил.
- `bridgeCheckSession()` — проверка **реальной авторизации**, а не HTTP 200:
  разбирается авторизованный вид главной страницы. Статусы (пишутся в лог как
  `[rutracker_bridge] status=…`): `empty`, `checking`, `authenticated (<аккаунт>)`,
  `unauthenticated`, `rejected`, `challenge`, `network_error`.
- `bridgeClearSession()` — сброс cookies и UA, не затрагивая вход в браузере.
- Легаси-вход RuTracker (логин/пароль) сохранён как fallback.

**Исправлено**

- Убран статический `User-Agent` из общего объекта `headers`. Ядро Movian
  (`http_header_merge()` в `src/fileaccess/fa_http.c`) сливает заголовки из опций
  запроса **после** заголовков inspector'а и перекрывает их, поэтому статический
  UA побеждал браузерный. Так как `cf_clearance` привязан к UA, ответом был
  `403 Cf-Mitigated: challenge`. Три per-link инспектора (`torrent`,
  `download.php`, `dl.php`) переведены на `bridgeUA()`.

**Известные ограничения**

- `debug: true` в оригинальных запросах плагина заставляет ядро писать
  `> Cookie: …` и `Inspector setting cookie …` в `movian.log`. Лог следует считать
  содержащим живые учётные данные. Не исправлено (вне объёма MVP).
- Cloudflare оценивает IP и TLS/HTTP-fingerprint независимо от cookies, поэтому
  перенос валидной сессии может не сработать.
- Не проверено живьём: поиск, раздача/magnet, истёкшая сессия, реальный challenge.

## Расширение — `Movian Cookie Bridge`

### 0.4.0 — 2026-10-18

**Безопасность**

- Movian host **по умолчанию только loopback** (`127.0.0.1`, `localhost`)
  вместо `confirm()` на каждую отправку. ТВ-приставка — через шифрованный
  туннель (`ssh -L`, `adb forward`) или по явной сохраняемой галочке
  «Разрешить передачу по локальной сети без шифрования» (осознанный риск;
  только частные адреса — `192.168.x.x`, `10.x.x.x`, `172.16–31.x.x`,
  `169.254.x.x`, `.local`/`.lan`; публичные отклоняются всегда). То же
  правило — `BridgeCore.movianHostAllowed()` — в Orca-тулзе (`--allow-lan`).
  Запросы попапа к Movian (`/api/diag`, `/api/open`) идут в режиме
  `no-cors`, поэтому приставке в LAN не нужны host-права. `::1` больше не
  считается loopback: HTTP-сервер Movian слушает только IPv4 (`AF_INET`), а
  голый `::1` давал невалидный URL (замечание ревью).
- Профиль RuTracker экспортирует cookies только `rutracker.org` /
  `rutracker.net` — те хосты, куда их отправит плагин. Ввод другого домена
  больше не отправляет в Movian cookies произвольного сайта.
- Перед чтением cookies — `chrome.permissions.request()` на конкретный сайт:
  сайты профилей разрешены заранее, новое зеркало HDRezka — через запрос Chrome.
- `http://*/*`, `https://*/*` перенесены в `optional_host_permissions`
  (кнопка «Захватывать запросы ко всем сайтам» для журнала запросов HDRezka).
  Убрано ненужное разрешение `tabs`. Для доменов профилей права есть на обе
  схемы: `chrome.cookies` отдаёт cookie без флага Secure (`bb_guid`, `bb_ssl`,
  `bb_t`) только при праве на `http://`-origin сайта (найдено живьём: с одними
  https-правами попап видел 2 cookies из 5). Через http ничего не отправляется.

**Изменено**

- Профиль — одна запись в `lib/bridge-core.js` (`settingsGroup`, `domains`);
  STPP-пути выводятся из группы, список профилей в попапе строится из ядра.
- Дубликаты имён cookies с разными Path: побеждает самый длинный путь;
  partitioned-запись по-прежнему побеждает unpartitioned.

### 0.3.2 — 2026-10-17

**Исправлено**

- `cf_clearance` не попадал в перенос. Cloudflare помечает его как partitioned
  (CHIPS), а `chrome.cookies.getAll()` возвращает только unpartitioned неймспейс,
  если не передан `partitionKey`. Наблюдалось живьём: попап показывал `Cookies: 3`,
  в запросе шли `bb_ssl`/`bb_session`/`bb_guid`, но не `cf_clearance`, и
  `viewforum.php` отвечал `403 Cf-Mitigated: challenge`. Теперь попап запрашивает
  оба неймспейса (`partitionKey: { topLevelSite: 'https://<домен>' }`) и объединяет
  их через `BridgeCore.mergeCookieLists()`; при совпадении имён побеждает
  partitioned-запись.

### 0.3.1 — 2026-10-17

**Исправлено**

- Запрос cookies по `url` заменён на `domain`. `chrome.cookies.getAll({url})`
  учитывает `path`, поэтому `https://rutracker.org/` возвращал только
  `cf_clearance`, теряя `bb_session`, `bb_guid` и `bb_ssl` (у них `path=/forum/`).
  Оригинальное расширение HDRezka использовало `url` и работало лишь потому,
  что cookies hdrezka.me лежат на `path=/`.

### 0.3.0 — 2026-10-17

- Адаптация оригинального расширения HDRezka под RuTracker: профили HDRezka и
  RuTracker с изолированными путями настроек, общее ядро `lib/bridge-core.js`.
- Кнопки «Send to Movian», «Очистить сессию», «Открыть сайт», «Открыть в Movian».
- Передаются только имена и количество cookies, значения не логируются;
  STPP — только on loopback, с подтверждением при отклонении от него.

### 0.2.0 — оригинал HDRezka

- Исходная версия «HDRezka Movian Cookie Bridge» только для `hdrezka.me`;
  профиля RuTracker в ней ещё не было.
